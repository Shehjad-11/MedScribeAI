# Hard Constraints & Operating Rules (rules.md)

> **Mandatory Rule:** The AI coding assistant (Codex) must NEVER violate the hard constraints defined in this file under any circumstances.

---

## 1. Non-Negotiable Hard Constraints

1. **No Clinical Fabrication:**
   - Never fabricate clinical claims, fake medical journal citations, or unverified treatment guidelines.
   - All AI prompt outputs and system instructions must strictly restrict information extraction to the user-provided consultation transcript and documented patient history.

2. **Physician Review Gate Preservation:**
   - Never remove or bypass the "doctor must review/approve" gate from any clinical flow, SOAP view, or print prescription slip.
   - All outputs generated by the AI must remain in a reviewable draft status until explicitly confirmed by the attending clinician.

3. **No Environment Secret Commits:**
   - Never commit `.env`, `.env.local`, API keys, or secret tokens into git tracking.
   - All secrets must be loaded via environment variables (`process.env.GEMINI_API_KEY`) and documented in `.env.example`.

4. **No Direct `node_modules` Modification:**
   - Never directly modify, edit, or touch files inside `node_modules/`.
   - Package installations or version adjustments must be executed via `package.json` with user consent.

5. **Schema Change Safeguard (`src/types.ts`):**
   - Always ask the user for explicit approval before making any schema or data-model changes to `src/types.ts`.
   - Any interface update (`SOAPNote`, `PatientInfo`, `SafetyAlert`, `EncounterRecord`) affects both backend (`server.ts`) and frontend components.

---

## 2. Commit Message Conventions

All commit messages in this repository MUST follow the **Conventional Commits** specification:

- `feat:` A new feature for the user or UI component.
- `fix:` A bug fix in logic, backend route, or rendering.
- `docs:` Documentation changes only (e.g., updating governance markdown files, README.md).
- `refactor:` A code change that neither fixes a bug nor adds a feature (e.g., splitting `SOAPNoteView.tsx`).
- `style:` Changes that do not affect the meaning of code (formatting, white-space, CSS tokens).
- `test:` Adding missing tests or correcting existing tests.
- `chore:` Updating build tasks, package configurations, or system settings.

*Example:* `feat(soap): split SOAPNoteView into modular section components`
